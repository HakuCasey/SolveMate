# 012 本机用户数据保存设计

## 数据归属

```text
user/
├── app.sqlite3
├── uploads/
├── community/
├── ai/
└── backups/
```

沿用已有 `AppData` 格式 3 和稳定编号，通过可选的 `readingProgress`、`drafts` 保存阅读进度和提问草稿。`packages/contracts/app-data.schema.json` 与 AI 共享 Schema 共同校验前后端边界；生成脚本同步 Python 包中的副本，CI 检查其一致性。对象关联、重复编号与默认教师另外检查，不从名称或文件位置重建关联。

`app.sqlite3` 的 `state` 表保存应用快照与修订号，`metadata` 保存数据目录标识；`versions`、`heads` 保存课程版本索引和当前指针，`migrations` 记录已处理的来源与内容摘要。沿用应用快照以保留现有业务操作，不在此次迁移中重写会话和笔记的数据组织方式。长会话的分页与增量存储继续单独安排。

上传资料继续使用原来的资料编号、版本目录和 `record.json`。AI 数据库保持原位，已有连接、原生编号、执行快照及工作目录不变。社区目录当前承接官方课程包，不表示已经提供社区上传或发布服务。

## 实现职责

- `storage/local-client.ts`：本机 HTTP 请求、浏览器缓存、服务状态和返回校验。
- `storage/migration.ts`：只读旧数据库、备份导入请求、来源回执和冲突选择。
- `storage/local-service.ts`：实现现有 `AppStorage` 接口，排队保存并检查目录标识与修订号。
- `storage/controller.ts`：页面更新、配置提交及后台回复的顺序；通过共用刷新机制读取其他浏览器的记录，比较未保存内容并处理冲突。
- `content/local-storage.ts`：本机课程包和版本指针的读取、保存与缓存；缓存校验失败时重新读取本机正式副本。
- `user_data.py`：SQLite 事务、课程文件落盘、浏览器备份与目录迁移。
- `user_routes.py`：`/local-api/v1/user/state`、`content` 和 `migrate` 接口，沿用本机来源与客户端标识限制。

学科目录与资料记录都由本机服务读取。上传数据接收完成、正式建立资料记录前检查当前学科，转移资料时也检查；删除的学科不能接收旧页面的新上传。文件与应用快照不是同一个事务，不用目录移动来模拟数据库关联。

官方资料的当前分类和删除状态保存在应用记录的可选 `officialMaterials` 数组；课程包与版本索引继续按来源课程保存。旧记录没有该数组时按原有分类读取，资料重新分类不改写历史引用或移动包文件。前后端使用同一 Schema 校验条目编号、学科编号和删除时间，并拒绝重复编号。

## 写入与缓存

保存使用 SQLite 事务和 `expectedRevision` 比较，旧值不能覆盖较新的记录。`storeId` 随数据库保存，目录整体移动不改变标识；页面打开期间连接到另一套数据库时拒绝直接写入。响应丢失后，相同内容与前一修订号可确认已提交结果，不重复增加记录。

浏览器的 `solvemate-server-cache` 保存读取副本和未确认修改。提交前保留候选值，本机确认后更新缓存并删除未确认副本；缓存写入失败与正式保存结果分别说明。每个窗口保存独立写入编号，启动时检查本窗口的未确认值及较早遗留值，不接管其他窗口正在提交的请求。恢复遗留值仍需要经过备份和冲突选择，不自动覆盖正式记录。课程保存响应丢失时重新核对本机当前版本；无法确认则说明结果未知，保留旧版缓存供阅读，不将未知结果显示为保存成功。

页面获得焦点及可见期间每 15 秒读取最新记录，存在未保存修改时按基线比较，互不覆盖的修改合并，同字段冲突由用户选择，规则见 [013](../013-data-refresh/design.md)。阅读位置合并保存，减少滚动事件的写入；当前页面、菜单、弹窗和临时选区不参与其他窗口的状态更新。草稿按现有对话或阅读范围编号保存。关闭前以页面保存状态为准。

本机服务不可达时，读取经过校验的缓存；没有缓存则提示启动本机服务，不能把连接错误当作空数据并创建示例。权限、数据格式或迁移冲突不通过缓存掩盖。服务恢复后重新检查未完成迁移；没有自动合并长期离线修改的逻辑。

## 迁移与失败恢复

1. 在原浏览器和原地址读取 `solvemate-local` 的原始信封及 `solvemate-content` 的所有版本、清单和当前指针。读取旧数据库不修改原值。
2. 将原始信封、历次格式备份和完整课程包写入 `backups/browser-<来源编号>-<摘要>.json`。后台计算摘要，文件临时写入、同步后原子替换。
3. 校验应用结构、关联和课程包。课程按固定编号与 SHA-256 版本写入 `community/`，写完文件后再在事务中提交应用记录、版本指针与迁移回执。失败可能留下未引用的完整文件，但不改变正式指针。
4. 已有不同正式记录时返回 `migration_conflict`。用户保留本机记录时，仅登记该来源已处理；用户选择替换时先通过 SQLite 备份接口保存本机数据库，再检查确认对应的版本并导入。已有课程历史文件继续保留。
5. 来源与内容摘要共同决定是否已处理。另一个浏览器的数据或旧页面后续写入的内容不同，需要重新备份和选择；不按时间推测哪份更正确。
6. 默认上传目录先复制到临时目录，逐文件比较 SHA-256，成功后启用 `uploads/` 并保存回执。复制中断不启用临时目录；启用后回执写入中断可在下次核对后完成。旧 `materials/` 不删除，显式配置目录不移动。

首次迁移前应关闭其他旧版页面。原页面后续产生的新记录仍保存在原数据库，下次打开新版可识别差异；程序不会静默清除旧数据库。

本次迁移备份不是通用备份管理界面。手工备份完整 `user/` 时应先停止服务；应用、上传文件、下载内容和 AI 关联应一同保留。

## 验证记录

验证使用独立目录、专用端口和独立浏览器站点，不修改用户正式记录，不调用 Codex 或其他真实模型。2026-11-12：220 项网页测试、19 项脚本测试、196 项本机服务测试与 24 项官方内容服务测试通过，本机服务另有 2 项按条件跳过。TypeScript、ESLint、Prettier、Ruff、依赖一致性和网页构建通过。

Chrome 使用两个独立站点缓存验证旧记录与课程包导入、另一处读取和改名、服务断开后的缓存阅读与草稿保留、恢复连接后的选择与备份、普通刷新及应用更新后的草稿恢复、重新打开资料后的答案状态。隔离测试保留原数据库，核对了正式索引、备份和包文件；未运行真实模型。

正式目录启用前确认没有进行中的 AI 请求或资料转换；旧资料逐文件核对 SHA-256 后启用新目录，并保留旧目录。已有对话消息、原生绑定、笔记和机器人与浏览器迁移备份核对一致。测试已纳入现有 macOS / Windows CI。本次检查在 macOS 执行，Windows 真机及其他浏览器的实际操作尚未验收。
